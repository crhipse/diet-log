# 생활연대기 자동 연동

## 사용자 연결

생활연대기 설정 → 자동 연동 관리 → 연결 코드 만들기에서 **식단 앱용** 코드를 복사한다. 실제 기록이 저장된 기존 아이폰 홈 화면 식단 앱의 설정 → 생활연대기 자동 연동에 한 번 붙여넣는다. 이후 식단 입력·수정·삭제, 식단 완료 표시, 날짜별 체중·영양 목표, 하루 시작 시각, 백업 병합·교체가 자동 반영된다.

원본 기록 저장은 서버 응답을 기다리지 않는다. 인터넷이 없으면 전송을 보류하고 앱 표시·재시작·온라인 복귀 때 재개한다. iOS에서 앱을 닫아 둔 동안의 백그라운드 전송을 보장하지 않는다. 설치한 앱을 삭제하거나 새로 설치하지 않아도 코드 업데이트와 연동이 가능하다.

식사 항목이 실제로 있는 날짜는 다음 날 **02:00 한국 시간**에 식단 완료로 자동 전환한다. 날짜 분류는 기존의 하루 시작 시각 및 식사 당시 시간대 설정을 유지한다. 앱을 열어 둔 동안에는 시각 경계와 주기 확인으로 반영하고, 앱을 다시 열거나 iOS의 이전 화면으로 복귀하면 이미 지난 날짜를 처리한다. 기존 대사량 행은 완료 상태와 수정 시각만 갱신하며 체중·활동·생성 시각은 보존한다. 식사만 있고 체중을 입력하지 않은 날은 화면에서 완료 상태를 계산하되 가짜 대사량 행이나 체중을 생성하지 않는다. 빈 날·체중만 있는 날·사진/메모만 있고 음식 항목이 없는 날은 자동 완료 대상이 아니다. 음식의 미입력 영양값은 그대로 null이다.

원본 행의 선택 필드 `dietCompletedAutomatically`는 자동 완료와 직접 체크를 구분한다. JSON 백업/복원에 보존되며 Dexie 버전 4 및 기존 6개 원본 테이블 구조를 유지한다. 연동 payload의 기존 `dietComplete`에는 직접 체크 여부만 투영한다. 생활연대기 서버는 이미 받은 실제 식사 수치에 같은 02시 규칙을 적용하므로 원본 앱이 닫혀 있어도 서버 조회 때 완료를 평가할 수 있다. 자동 완료만으로 같은 수치 digest를 다시 전송하지 않는다. 해당 날짜의 음식을 모두 삭제하거나 날짜 설정 변경으로 다른 날로 이동한 경우에는 자동으로 붙인 완료만 해제하고, 사용자가 직접 체크한 완료는 유지한다.

빈 브라우저 저장소를 연결했는데 서버에 기존 식단 기록이 있으면 전송을 중단하고 기록이 있는 기존 홈 화면 앱을 안내한다. 서버가 겹친 직접 입력을 발견하면 식단 앱에는 전송 완료와 함께 생활연대기 확인 필요를 표시한다. 생활연대기에서 기준을 선택해야 해당 충돌이 해결된다.

## 데이터와 보존

전송 대상은 식사별 ID·섭취 시각·당시 시간대·8종 영양 수치, 하루 시작 시각, 날짜별 체중·식단 완료 상태, 날짜별 영양 목표다. 기존 importDiet 어댑터가 논리 날짜와 당시 목표를 계산하도록 원본 구조를 유지한다. 미입력 영양은 null이고 AI 분석 완료는 식단 완료로 취급하지 않는다.

사진·음식명·양 설명·자유 메모·AI 분석 응답·모델·API 키·활동 이름은 명시적 허용 목록에서 제외한다. 동기화 큐는 백업을 변형해 만드는 방식이 아니라 이 수치 투영만 저장한다.

Dexie v4에 chronicleSync 테이블만 추가했다. 기존 6개 테이블을 이동·삭제하지 않는다. 연결 토큰·일회용 코드 교환 대기·기기 ID·revision·전송 대기·확인 digest는 이 테이블에만 둔다. 기존 JSON/사진 포함 백업과 Markdown/CSV는 이 테이블을 읽지 않는다. 백업 교체도 이 테이블을 지우지 않는다. 앱 내부 연결 해제는 이 테이블의 연결 정보만 지우고 원본 기록과 서버 기록은 유지한다. 서버 토큰 폐기는 생활연대기에서 수행한다.

## 재시도와 동시성

- 원본 세 테이블(records/settings/dailyMetabolismEntries)의 커밋을 Dexie liveQuery로 감지하고 짧게 묶는다. 앱 시작 시 현재 수치 SHA-256 digest를 마지막 서버 확인 digest와 비교하므로 원본 저장 직후 앱이 종료되어도 누락을 복구한다.
- 읽기·큐 갱신은 같은 IndexedDB transaction으로 직렬화한다. 탭 간 전송은 지원되는 브라우저에서 Web Locks를 추가 사용한다. Web Locks가 없어 중복 전송되어도 불변 pending 및 revision 검증으로 동일 요청만 중복될 수 있다.
- 네트워크 실패/5xx/429/408 및 응답 유실은 동일 mutationId·revision·payload를 그대로 재전송한다. 전송 도중 수정은 latest로 보관하고 앞선 응답이 새 입력을 지우지 못한다. 확인된 값으로 다시 취소한 경우도 앞선 전송 뒤에 되돌린 값을 전달한다.
- 400/422/413 및 empty_initial_snapshot 확정 거부는 같은 실패 digest의 자동 재시도를 멈춘다. 원본 수치가 바뀌면 새 revision으로 복구한다. 401/403은 새 연결이 필요하다. 오래된 revision 응답은 서버 revision 이후에 현재 전체 투영을 보낸다.
- 응답 헤더와 JSON 본문 전체에 15초 제한을 걸며, 제한 이후 늦게 온 응답은 큐를 변경하지 않는다. 로컬 크기 검사 및 서버 413 모두 큐를 보관하고 부분 스냅샷을 보내지 않는다.

## 브라우저·서비스 워커

CSP connect-src에 `https://life-chronicle.crhipse.workers.dev`만 추가했다. 요청은 credentials omit, cache no-store, redirect error이며 사용자 지정 서버 주소를 받지 않는다. CORS는 서버의 원본 `https://crhipse.github.io` 허용 설정이 필요하다. 서비스 워커는 기존 PWA 범위를 유지하고 Workbox의 자기 scope precache만 정리한다. cross-origin runtime cache 규칙을 추가하지 않았으므로 연동 POST나 토큰 응답을 캐시하지 않는다.

## 검증과 배포 담당자 확인

`pnpm test`, `pnpm build`를 사용한다. 새 테스트는 수치 허용 목록·누락 영양·목표/체중/날짜 이력, 코드 교환 유실, 오프라인 재시작, 불변 재전송, 전송 중 되돌리기, 요청/본문 시간 초과, 연결 해제 후 늦은 응답, 확정 거절 복구, 탭 동시성, 실제 저장·삭제·목표·체중·백업 경로 관찰, 비밀 백업 제외, v3→v4 기존 자료 보존을 다룬다.

배포 후 기존 홈 화면 앱에서 업데이트를 받고 실제 기록이 그대로 보이는지 확인한다. 게임에서 식단용 코드를 발급해 연결하고 식단 수치 수정·완료 토글·과거 날짜 수정·목표 및 체중 변경·삭제·오프라인 입력 후 재실행을 확인한다. 이 변경 작업은 소스와 검증만 작성하며 실제 GitHub Pages 배포 및 사용자의 iPhone 연결은 상위 작업에서 진행한다.
